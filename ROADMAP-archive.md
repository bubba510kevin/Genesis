THREE REAL BUGS IN GENESIS'S OWN LOCKS were found by this, and they were not network bugs. (1) The interrupt flag was saved IN THE LOCK, which is correct only for strictly nested release; the network stack releases out of order constantly, and the result was interrupts left disabled forever three ticks after the first ARP request. It is a per-CPU nesting count now, which is what FreeBSD's spinlock_enter/exit does. (2) rw_try_rlock was mapped onto try-WRITE, so a caller that released as a reader drove the count to -2 and corrupted the lock. (3) rw_try_upgrade returned unconditional success, so a caller believed it had exclusive access while still holding a read lock. All three are fixed in kernel/lib/mtx.c, which also grew a bounded-spin deadlock report and a held-lock dump — the tools that found them.

NEW — AND IT IS BLOCKED, on four things Genesis does not have, each of which is its own item rather than a detail of this one. Listing them because "vendor more ZFS" is not actionable and "build these four, then vendor ZFS" is:
(1) KERNEL THREADS. The txg sync thread, the ARC reclaim thread and the ZIL commit path are real threads that block and are woken. kernel/bsd/kern_synch.c's own header states the gap from the other side: sleep(9) there IDLES the CPU rather than descheduling, because sched.c schedules processes with user address spaces and has no concept of a schedulable kernel thread. Everything else on this list depends on this one.
(2) CONDITION VARIABLES and sleepable taskqueues. cv_wait/cv_broadcast appear throughout the DMU and the ARC. kernel/bsd/compat/sys/taskqueue.h currently runs a task INLINE on the enqueuing CPU, which is correct for what uses it today and is not a taskqueue.
(3) A PAGE CACHE WITH WRITEBACK. ZFS's read path is built on ARC buffers handed to the VM; the write path is dirty pages flushed at txg commit. Genesis has a BLOCK cache (kernel/fs/bcache.c, 64 4KB blocks) which is a different thing at a lower layer, and no file-backed mmap at all (sys_mmap answers -ENODEV for anything but MAP_ANONYMOUS).
(4) A REAL kmem_cache WITH RECLAIM. UMA is vendored (uma_core.c, item 11 Part 12) so the allocator exists, but nothing raises vm_lowmem — kernel/bsd/uma_vendor.c says so directly, and the ARC is a cache that is only correct if something can tell it to shrink.

NEW — the honest sequencing, then, is: kernel threads first (they unblock (2) and make sleep(9) real rather than an idle loop); then condvars and a real taskqueue; then vendor module/zfs's READ path (dmu/dbuf/dnode/zap/dsl/zio) which gets the full read feature set and is testable against the same pools the bootloader reader already mounts; then the ARC once there is something to reclaim under; then the write path, which is the first point where a bug destroys data rather than failing a read. Feature-flag gating stays the entry check throughout: a pool with a feature this build does not implement must be REFUSED, not mounted read-only-and-hope, because ZFS's whole compatibility story is that an unknown incompatible feature means the on-disk format is not the one this code understands.

NEW — THE VFS WORK THE ROOT FLIP NEEDS, which is a separate prerequisite from any of the above and is small enough to do first. Flipping root to ZFS means the root filesystem is one whose vtable slots are mostly NULL today, and four things break at that moment:
(a) fs_ops_t HAS NO unmount SLOT. kernel/zfs/zfs_vfs.c documents this against itself: fs_unmount_volume removes the mount-table entry and never tells the filesystem, so a ZFS slot is taken by a successful probe and never released, and a machine that has seen four pools stops recognising the fifth. Harmless for FAT, not harmless for a root that can be remounted. This is the one item on this list that is a bug rather than a missing feature.
(b) NO write SLOT ON EITHER FILESYSTEM. fat16 implements the four NAMESPACE slots (mkdir/rmdir/unlink/rename) and leaves `write` NULL, so file CONTENT is read-only everywhere in this kernel. A root that cannot be written is not a root.
(c) NO SYMLINKS BELOW THE VFS. The object namespace has them (ns.c); fs_ops_t does not. readlinkat is in the syscall table with nothing on disk to resolve. ZFS has symlinks and a root filesystem that silently cannot represent one is a root that cannot hold /bin/sh -> busybox.
(d) NO PAGE CACHE, so exec of a large binary off ZFS re-reads it through the block cache every time. Tolerable for a second volume, not for the volume every execve comes from.

NEW — and one thing to check rather than assume when the flip happens: the NT side reaches a volume through the object namespace (\Device\HarddiskVolumeN + an unparsed remainder, consumed by dev_open_object -> vol_parse -> fs_lookup_on) and DELIBERATELY skips the mount table. That path is filesystem-agnostic today because vol_parse only converts separators, but it has never been exercised against a filesystem whose lookup is not FAT's. The check is the one already written down for this item - systest's filesystem section running identically on both volumes - extended to run through both spellings.

FAT16 was picked as "the sane first target" (build.py's own comment) specifically because its root directory is a fixed-size array rather than a cluster chain, which was the right call before a filesystem vtable and a real second-filesystem reader existed; both now do. Keeping FAT16 as the permanent default after that decision was made moot is exactly the kind of no-longer-load-bearing simplification item 11's own list above is for - except this one is a forward architectural decision (what root becomes), not a stub to revisit once a prerequisite lands, so it belongs here as its own line rather than folded into the grouped backlog above. Concretely: finish item 7's write path and dirty-journal handling, then make a ZFS root the default `python3 build.py disk` produces, with FAT16 demoted to (or replaced entirely by) whatever item 1's mounting/drive-letter work still needs it for.

12. Write drivers needed for basic operation (choose what driver model best suits what the driver does the best based on their ecosystem strengths, ABI stability, and performance characteristics.)
NEW — keyboard.c, rtc.c, disk.c, and timer.c already exist as ad hoc drivers predating any of the three models; worth an explicit pass deciding which model each migrates to versus staying bespoke because they're boot-critical, rather than starting from a blank page

NEW — the decision, worked per category rather than left as an abstract principle: storage (ATA/AHCI/NVMe) is Newbus — ata.c+disk.c is already conceptually a two-layer Newbus driver (raw hardware talk, then a device_ops_t adapter), it is the same ecosystem ZFS is already vendored from, and its direct synchronous call shape fits this kernel's uniprocessor polling-first storage path better than Linux's block layer or WDM's IRP-per-request overhead. The two NICs item 6 already names, virtio-net and e1000, are Newbus too, ported straight from the real drivers already sitting in vendsrc/sys/dev/virtio and vendsrc/sys/dev/e1000 — no reason to reach for a translation layer when a native, well-tested driver for the exact target hardware already exists in the vendored tree. Wifi and anything newer or less common is Linux-shaped instead: vendsrc/sys/contrib/dev (rtw88, rtw89, iwlwifi, iwm, iwn, mwl, athk, mediatek, ...) is FreeBSD's own admission that these are a source-compat-with-Linux-driver-code problem, not a from-scratch-native one, and the same reasoning will apply to any GPU driver beyond a basic framebuffer — FreeBSD's own DRM story is LinuxKPI-hosted for exactly this reason. Input (PS/2 now, USB HID later) and RTC/timer/system peripherals stay Newbus: simple, standardized, already native, no ecosystem reason to diverge. WDM/KMDF's role is different in kind from the other two rather than a third slice of the same pie — it is the only path to binary compatibility with a driver that has no available source anywhere, the proprietary-Windows-only case (laptop ACPI/embedded controllers, audio codecs, some GPUs), which is also why /wsr/Windows/System32/Drivers is a real load path in item 4's text rather than a decoration: it names loading a driver out of an actual Windows installation tree. Until the kernel-mode PE loader and NT export surface item 4 already flags exist, WDM-shaped code here means driver source written natively against that shape same as the other two, but the eventual payoff — unmodified binaries — is categorically different from what Newbus or the Linux shim ever offer.

NEW — the matching engine underneath all three models stays Newbus-shaped (bus.c's devclass/probe/attach), but two pieces of the real WDM architecture are genuinely better than anything Newbus has, not just differently-shaped: IRP-based dispatch, where a request is a queueable, cancelable object with a completion routine rather than a blocking function call — device_ops_t and Newbus's attach() are both fundamentally synchronous-call-shaped, and neither has an answer for overlapped or in-flight-cancelable I/O if a NIC's TX ring or USB's concurrent transfers ever need one; and device stacking (IoAttachDeviceToDeviceStack), layering a filter driver — disk encryption, RAID — on top of another device's object, which Newbus's flat parent-child devclass tree cannot express at all (FreeBSD itself does not solve this in newbus either; it reaches for GEOM, a separate stacking system, for exactly this reason on the storage side). Neither is worth building now — Genesis is uniprocessor, synchronous, and one-driver-per-device by device.h's own existing design — but the day a real hot-pluggable bus (USB) or a filter-driver use case (disk encryption above the storage stack) shows up is the day reaching for WDM's actual IRP/stacking model, not just its type shapes, over bolting the same thing onto Newbus is the right call.

NEW — 13. SMP bring-up
Currently assumed-but-undated in three places: EFER.NXE per-CPU (Owed), netinet's locking primitives (item 6), and ULE's own stated precondition (item 8) all wait on a second CPU existing. AP startup (INIT-SIPI-SIPI), per-CPU data extended from the existing cpu0 struct, TLB shootdown, IOAPIC routing past the BSP, and the locking primitives item 6 already needs — worth building once as its own item rather than three times as side effects of other items

DONE — landed as Part 10 of the item 11 pass, and it was the hinge the rest of that pass turned on. ACPI MADT parsing for the CPU list (kernel/acpi.c); a Local APIC driver (kernel/lapic.c); a real-mode AP trampoline (kernel/ap_trampoline.c, in its own .text.aptramp section — putting it in .lowtext displaced _kernel_entry and booted to nothing); INIT-SIPI-SIPI bring-up with per-CPU GDT/TSS, per-CPU IST stacks and per-CPU %gs base (kernel/smp.c); and IPI-driven TLB shootdown. All three things this item said were waiting on it are now closed: EFER.NXE is set per-CPU in the AP trampoline's own wrmsr, item 6's locking primitives are real (kernel/mtx.c), and item 8's ULE is the live policy.

The two lessons worth keeping. Each CPU needs its OWN LAPIC enable — an AP that reached its C entry point fine still answered zero IPIs until lapic_init_ap existed, because "the LAPIC is on" is not a machine-wide property. And a shared TSS means a shared rsp0 and shared IST stacks, which is silent corruption rather than a fault, so per-CPU GDT/TSS is load-bearing rather than tidiness.

Verified by kernel/smp_selftest.c and kernel/lock_selftest.c at boot under -smp 2, with the -smp 1 path confirmed unchanged.

DONE — the IOAPIC too, which was the one piece this item left open. kernel/arch/ioapic.c programs the redirection tables the MADT describes (kernel/arch/acpi.c now collects IOAPIC and interrupt-source-override entries on the same walk it already made for CPUs), masks the 8259 pair, and carries the existing mask state across the handover so the timer and keyboard stay live without anyone naming them. Legacy lines keep vector 32+irq, so interrupt.c's dispatch, irq.c's tables and every driver's irq_register call are unchanged — only the wire differs. What is NOT unchanged is acknowledgement: an APIC-delivered interrupt takes lapic_eoi and a PIC-delivered one takes pic_send_eoi, so interrupt.c calls irq_eoi and that one function answers "which controller" for the whole tree.

The trap, and it is the only real one in IOAPIC bring-up: an ISA IRQ number is not a GSI. The MADT's interrupt source overrides say so, and on QEMU — as on essentially every machine with an IOAPIC — the timer comes out on GSI 2, not GSI 0. Confirmed by A/B: with the override table ignored the entry reads "irq 0 -> gsi 0" and looks perfectly correct, and the machine never ticks again.

Verified by kernel/arch/ioapic_selftest.c. The discriminating check is that the 8259 masks read back ff/ff — booting proves nothing on its own, since if the PICs had been left live every legacy interrupt would still arrive by the old path and the log would be identical whether or not a single redirection entry was right. With both masked, a tick arriving is real evidence. That A/B also fixed an ordering bug: every post-sti selftest waits on ticks, so a broken handover hung them all before anything could say why; ioapic_selftest now runs first and is bounded by a spin count rather than by a second tick.

Still open on this item: no interrupt balancing. Every line is routed to the BSP and stays there. Choosing a destination per line is possible now (ioapic_route_irq takes an APIC ID) but deciding it dynamically is policy with no measured problem behind it.

NEW — 14. Finish the NT object manager and namespace

What exists: kernel/obj/object.c (refcounted object_t behind an object_type_t vtable - read, write, getdents, poll, destroy) and kernel/obj/ns.c (a tree of ns_entry_t, kinds DIRECTORY/LINK/OBJECT, backslash-separated, case-insensitive, with the UNPARSED REMAINDER rule that lets one namespace address filesystems and character devices without knowing what either is). dev_open_object is the single place a remainder is consumed. ns.h states the design decision that makes this item worth finishing rather than trimming: the namespace is NT's and the POSIX spelling is layered ON TOP rather than beside it, because two namespaces would mean two sets of names for one console.

What is in it today: \Device\Console, \Device\Null, the disks and volumes, and the \??\ links (CON, console, tty, stdin, stdout, stderr, null, NUL, C:, sda, sdb). Devices and links to devices, and nothing else.

NEW — DISPATCHER OBJECTS are the biggest gap, and they are the half of the object manager that has no substitute anywhere else in the kernel. NT's namespace exists at least as much to let two unrelated processes agree on a synchronisation object BY NAME (\BaseNamedObjects\SomeMutex) as it does to name hardware - a Win32 program's first kernel call is very often CreateMutexW rather than CreateFileW. Three types, and the differences are visible to a waiter so they cannot be collapsed into one: an EVENT is a flag, where a notification event stays set and releases every waiter and a synchronisation event releases exactly one and auto-resets; a SEMAPHORE is a count with a limit, and a release past the limit must be REFUSED rather than clamped, because a caller that over-releases has a counting bug and clamping hides it forever; a MUTANT is ownership and is RECURSIVE - the owner may take it again and must release it as many times, which is exactly why it is not a semaphore of one. object_type_t needs two more slots for this (a wait that BLOCKS and a signal), and the pairing with the existing poll slot is the thing to get right: poll asks "would this block", wait performs the operation and CONSUMES - a synchronisation event resets, a semaphore decrements, a mutant takes ownership - so wait cannot be built out of poll and must not be called speculatively.

NEW — and the prerequisite that decides when: kernel/proc/waitq.c blocks a PROCESS, so a wait through it is only legitimate from a syscall path. A driver waiting from kernel context has nothing to deschedule, which is the same boundary kernel/bsd/kern_synch.c describes from the other side and the same one item 7's ZFS work is blocked on. So the userland half (NtCreateEvent/NtWaitForSingleObject) is buildable now on waitq; the driver half (KeWaitForSingleObject with a real KEVENT) waits on kernel threads. Worth building in that order rather than waiting for both.

NEW — THE HANDLE TABLE IS NOT ONE. handle_t carries a per-descriptor flags word and points at an open_file_t; there is no GRANTED ACCESS MASK on the handle, so the access argument that NtOpenFile and open(2) both take is used to choose a mode at open time and then never enforced again. NT's model is that the mask is checked at every operation, and that is what makes a read-only handle to a writable file mean anything. Also absent: OBJ_INHERIT semantics beyond the one HANDLE_INHERITABLE bit, and any notion of a handle table that is not the fd table.

NEW — NO SECURITY DESCRIPTORS, so OBJECT_ATTRIBUTES carries a path and nothing else. That is defensible while there are no credentials (kernel/bsd/net_absences.c makes the same point from the network side: there is one ucred and it is the unrestricted one), and it stops being defensible the day there is a second user. Sequencing note: this is downstream of a real credential in struct process, which item 9's syscall work is the natural home for.

NEW — TYPES ARE NOT NAMED. Real NT has \ObjectTypes\ with one entry per registered type, which is what makes the namespace self-describing and what a tool walking it needs to know whether it is looking at a Device or a Section. Genesis has object_type_t.name and nothing publishes it. Cheap to add and worth doing at the same time as the dispatcher objects, since that is when the type list stops being all-devices.

NEW — MISSING DIRECTORIES: \BaseNamedObjects (where the dispatcher objects go), \KernelObjects, \ObjectTypes, \Sessions. And the pools are small - NS_MAX_ENTRIES 64, NS_NAME_MAX 32, NS_PATH_MAX 128 - which is fine for eleven entries and is not fine once every named event is one.

NEW — ONE INCONSISTENCY THAT IS ALREADY A BUG-SHAPED THING: device_ops has a `control` slot documented as "everything that is not a byte transfer: geometry, eject, media-change polling, and later an ioctl surface", and sys_ioctl does not dispatch through it. sys_ioctl is a hardcoded `fd > 2 -> -EBADF` plus a termios table, so the mechanism for device control exists, is documented, and has no caller. Either wire it or say in the header that it is unreachable; leaving it as it is means the next person to add a control code will find it does nothing.

NEW — the check for this item, in the shape this tree uses: a named event created by one process and opened by name from another, with the second one BLOCKING until the first signals - a test that only creates and signals in one process cannot tell a real wait from a function that returns immediately. Plus the negative: waiting on a console must answer -EINVAL rather than hanging, and that has to be asserted or the "not waitable" path is indistinguishable from a type nobody has got to yet.

Owed
DONE — the boot image no longer has a size cap to raise. It used to load at 0x7E00 and grow upward toward the 32-bit stack boot.asm sets up at 0x90000, so 557568 bytes was a hard wall and build.py carried a MAX_IMG_SIZE that had been raised by hand five times, the last landing within 512 bytes of it. The kernel loads at 0x100000 now: boot.asm enters unreal mode and copies each INT 13h chunk up out of a low bounce buffer, because INT 13h cannot write above 1MB. Nothing sits above the kernel there, so the only remaining bound is KERNEL_MAP_SIZE — a page-table constant costing .bss rather than image bytes, raised to 16MB — and build.py READS both that and KERNEL_LMA out of the files that define them rather than duplicating either. Two things fell out of the move: A20 had to be enabled before the copy rather than after (with the gate shut, every write above 1MB silently wraps into the megabyte below), and the sector's own code grew past byte 446 and into the MBR partition table area, where Genesis's own partition scanner read the GDT as a partition entry. The table is explicitly zeroed and padded to now, so NASM fails the build if that ever recurs. The kernel doubled in size in the same session and the check now reports 7% of the window used.

VERIFIED AGAINST A REFERENCE IMPLEMENTATION, which is the part that counts for a filesystem writer: systest's 27 new checks only prove Genesis agrees with itself. /bin/mkprobe creates and renames a nested tree and leaves it, and the host then reads it with `mdir` and validates it with `fsck.fat -n -v` — no errors, meaning both FAT copies agree and no cluster leaked. unlink was checked by arithmetic rather than by absence: a 12KB file on 2048-byte clusters is six of them, and fsck's cluster count fell by exactly six.
